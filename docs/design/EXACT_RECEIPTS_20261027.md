# Exact message observations — contract-first increment

The C04 follow-up found both current personal clients collapse a visible set to its newest message and the backend interprets that as a timestamp prefix. This can acknowledge skipped/unloaded content and distinct messages with equal timestamps. The prior privacy-generation fix remains valid but does not solve visibility identity.

Target contract: acknowledge a bounded, explicit set of received message IDs, with independent private delivery/read state and consented public observations for each message and current membership epoch. Read implies delivery of that message only. Replays, preference toggles, unblock and membership reuse must not promote private observations. A sender must never become their own recipient. Invalid/foreign batch IDs reject atomically. Pending/spam/declined requests cannot emit receipts. Current account/business/thread authority applies on every call; restricted contacts may clean up private observations without publishing them.

Use the existing `messageReceipts` table. Its legacy rows are not evidence of current consent; new optional membership/consent metadata must be present to project a public receipt. A receipt reader returns only aggregate state for the sender's one exact message, with no reader identities/times/private state. Group state requires every currently eligible original recipient; later members are excluded, left/rejoined or inactive members cannot lend stale evidence. No empty-set read success. Each read is bounded to one message and the existing 1,024-member group limit, avoiding page-size multiplied fanout. Larger channels need a separate qualified contract and must not claim group consensus.

This increment implements and tests the canonical write/read contract first. It does **not** switch either UI producer, advertise an enabled capability, change private unread badge semantics or remove old endpoints. The next increment must wire both clients together: exact visible IDs, loaded-message delivery, retries/cancellation on account/route/background changes, per-message receipt rendering and exact private unread accounting without guessing/backfilling historical cursor observations. Activation/release stays held until that path is integrated and verified. Legacy timestamp-prefix behavior remains a required gap, not a completed fallback.

Use synthetic records only. No publication, production data backfill, real messages/settings, provider activity, native permissions or push activation. Existing APKs and prior receipts remain untouched. Physical/two-account/deployed acceptance remains separate from this contract proof.

## Implemented contract

- `messaging/receipts:acknowledge` accepts 1–100 explicit message IDs and `read` / `delivered`. It validates the full batch before writing, deduplicates IDs and records only received, non-deleted, non-blocked content. It never advances the legacy private/public timestamp cursors. Current active identity, membership and company authority are enforced before observation; read-only/frozen history can be observed without authorizing a send.
- Each receipt row binds the membership ID, join time and independent `receiptEpoch`. Public delivery and read generation are distinct from private `state` / `at`. Duplicate delivery/read calls never rewrite state/time or promote a private read after enabling sharing/unblocking. A first read after an earlier delivery is a fresh observation and can publish its current consent. Legacy private rows without epoch proof are not backfilled; an already-read legacy replay cannot manufacture consent.
- `messaging/receipts:state` returns only null / sent / delivered / read for the authenticated sender's one exact message. It does not return private timestamps, recipient IDs or consent generations. Personal and group contacts reuse current block/family/request rules. Group consensus requires all current eligible original recipients; later joins and revoked business members cannot provide evidence. No eligible recipients yields sent. Unsupported channels/E2EE and groups beyond 1,024 members yield no qualified consensus.
- Rejoining through invitation, public thread join or salon join increments a monotonic receipt epoch and clears old private/public cursor metadata. Request acceptance does the same. This prevents old evidence surviving reused membership rows even if join/removal/acceptance occurs within one clock tick; join time alone was insufficient. Existing independent pins/mutes are unaffected.

Optional schema metadata only: `threadMembers.receiptEpoch`, plus `messageReceipts.membershipId`, `membershipJoinedAt`, `membershipEpoch`, `publicDeliveredAt` and `publicReadGeneration`. The existing receipt indexes are reused. No new table, index, data repair or backfill was executed. Generated client API references and capability/UI activation belong to the next integration increment; no client advertises this feature yet.
