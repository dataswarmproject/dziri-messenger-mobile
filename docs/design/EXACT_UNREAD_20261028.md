# Exact private unread tracking — backend integration increment (28 October)

The exact-receipt contract is prepared but neither UI is activated. Timestamp-prefix private unread cursors would still clear skipped messages if those clients were switched now. This increment replaces that dependency for prepared personal memberships with a private indexed unread ledger, retaining canonical message history and separate public receipt consent.

Use a private `messageUnread` row per received message/user, bound to membership ID/receipt epoch and a private dismissal generation. Explicit preparation captures the old private unread floor, clears legacy public prefix evidence and initializes historical unread metadata in bounded scheduled pages. New canonical sends add entries atomically for prepared memberships, so arrivals during initialization are never missed. Until initialization is complete, a summary is explicitly unknown; it must never report a partial scan as zero. Historical initialization only affects private metadata and does not invent a public observation. Real initialization/backfill is not authorized in this local pass.

Exact read acknowledgements remove only the named unread entries; delivery alone does not. A message read before its initialization page is processed cannot be resurrected. Mark-as-read is private dismissal, not a read receipt: advance a private generation rather than deleting or publicly acknowledging unviewed history. New arrivals use the new generation. Queued initialization is bound to epoch/generation/cursor and must stop after revocation, rejoin or dismissal. Independent observation revisions reject old read callbacks after a manual unread/dismiss action. Prepared exact acknowledgements require the expected epoch and revision; old timestamp endpoints must not publish new exact evidence.

Deleted/restricted messages leave no visible unread count; reversible moderation preserves the private marker and restores it only in its original epoch/generation. All canonical personal message writers must use the same fanout, including text/media/forward/Story replies and call-history rows. Existing unsupported channel/E2EE counting is unchanged and is not qualified by this increment. Counts are bounded at 100 (the existing 99+ display), with manual unread markers preserved.

This is local implementation and synthetic transactions only. No client capability activation, production jobs/migration, schema publication, real messages/moderation/settings, provider operations, push or replacement APK. The next increment must wire both clients' visible batches, receipt/unread subscriptions and scope cancellation together, then qualify their actual UI and live/device journeys.

## Implemented locally

- `unread:prepare` and `unread:summary` require current active account/thread/business authority. Preparation captures the existing private floor (and join boundary), clears legacy public prefix metadata and schedules initialization in pages of 100 messages. Duplicate/resumed jobs compare membership epoch, private generation and stored cursor. Suspension/revocation stops initialization; an authorized later preparation can resume it. No public observation is inferred from this work.
- `messageUnread` stores private IDs/ownership/scope/visibility only, with indexed per-member counting capped at 100 and an owner index for subsequent privacy lifecycle work. It has no message bodies or public status. Current exact read proofs prevent initialization from resurrecting already-observed messages. Private dismissal advances a generation, so it cancels historical work without clearing later arrivals. Independent revisions reject stale observation callbacks after manual inbox actions.
- All five direct personal message insert sites are integrated: canonical text (including forwards and Story replies), media, ciphertext (explicitly skipped as unsupported), and both call-history insertions. Live fanout uses current prepared memberships rather than comparing the message clock with join time; a backwards clock cannot lose a newly committed arrival. Historical initialization conservatively respects the old private floor and join boundary. Idempotent command retries create no second unread entry.
- Exact acknowledgement removes only named private entries. Delivery does not. Prepared calls require the expected epoch/revision. Legacy timestamp read calls on a prepared membership can clear one private ID but cannot publish new exact proof or clear a prefix; legacy delivery adds no public evidence. Manual mark-as-read is private cleanup on both prepared and legacy memberships, never an assertion that unviewed history was read.
- Both existing inbox query families and the total badge consume the same prepared private counts. Lists carry `unreadCountComplete: false` during initialization/visibility work; the new summary exposes null until ready. Legacy numeric-only callers retain a nonzero placeholder while work is unknown. Both UI adapters must respect readiness when they are switched; unchanged old clients do not establish complete new-flow acceptance.
- Deletion, editable legacy visibility changes, report restriction and moderation reversal refresh private visibility. Propagation is paginated, versioned and cursor-bound. A thread remains explicitly unknown while propagation is incomplete, including restoration; stale restriction jobs cannot undo a reversal or revive a dismissed generation. No message history is deleted by unread cleanup.

New schema: private `messageUnread` table with four indexes; one indexed prepared-membership lookup; optional membership preparation/revision metadata, a thread pending-visibility count and message visibility-job metadata. No actual production table initialization, migration, historical data repair or function/schema publication ran. Existing generated API references are not refreshed and no feature capability is advertised yet; the scheduled internal references use the existing repository pattern of typed named references.
