# Receipt audience identity and unread privacy lifecycle

The exact-unread checkpoint is local and both UIs remain unactivated. Its next blockers are original group-recipient identity (the public prototype still compares clocks), and the new private unread table's account lifecycle.

Required recipient contract: each newly committed DM/group message binds an authoritative membership-cohort revision inside the send transaction. Initial cohort capture records every current membership once. Later joins/rejoins advance a monotonic revision and bind that membership; clocks are never used to infer who originally received a new message. Public consensus still checks current membership/receipt epoch/account/business/contact/privacy state. Later memberships cannot block or manufacture old consensus. Request acceptance rotates observation authority without pretending the recipient identity changed. Historical group messages without cohort evidence remain unknown rather than being backfilled from current members. Historical 1:1 exact observations may use the current canonical peer; old private cursors are never public evidence.

Store only a thread revision, each current membership's cohort-start revision and each new message's cohort revision, avoiding a recipient array on every message. Existing canonical send hooks cover all personal writers. All join/rejoin entry points must update the cohort transactionally, including same-clock changes. New cohort initialization and queries remain bounded to the approved 1,024-member limit; malformed/missing cohort evidence fails closed. No new membership, permission, provider or encryption flow is authorized.

Required privacy contract: the owner-indexed `messageUnread` table participates in canonical account deletion and bounded participant-only data export. Export only the owner's private marker/reference state; omit other users, content, consent generations and internal membership/cursor fields. Purging one user's ledger cannot delete another user's entries or message history. Queued initialization cannot repopulate a deleted/deleting account. Soft-delete/moderation propagation and hard purge must be distinguished; no real account/data actions or migration are authorized in this local work.

Source/schema/index publication, real cohort preparation/initialization/export/deletion, UI capability activation, real communications, providers and push remain held. Use synthetic transactions and preserve all earlier receipts and APKs. Both client integration/rendering and actual device/two-account qualification remain required after these backend prerequisites.

## Implemented locally

- `receiptAudience.ts` binds every newly committed personal DM/group message to a membership-cohort revision through the existing five writer hooks. The first new message captures current memberships once; subsequent messages store only a revision. No per-message recipient array and no historical cohort backfill is created. Group initialization is bounded at 1,024 memberships; overflow rejects the complete send transaction. Integer/range checks reject impossible cohort metadata instead of dropping a recipient from consensus.
- Invitation, public join and salon join/rejoin update the cohort in their existing transaction. Joins after a message have a greater cohort-start revision, including the same clock tick; a backwards clock does not omit a real recipient. Current account/business/membership/contact/read-sharing and observation-epoch checks remain in force. Request acceptance resets observation evidence while preserving the original recipient identity. No roles, keys or permissions are provisioned by this mechanism.
- Historical groups without original-recipient cohort evidence return unknown. Current canonical 1:1 partners can still provide fresh exact observations; legacy private cursors remain insufficient. The old exact-receipt group fixtures now seed real new-message cohort evidence and use actual join/send ordering, with a separate regression proving legacy group consensus stays unknown. No acceptance assertion was weakened into a guessed historical read.
- `messageUnread` is in the canonical personal account-deletion allowlist via its owner index and therefore in the export catalogue. The explicit export projection returns at most 500 owner marker references, labels current/retired scopes and reports truncation. It omits content, peer identities, internal membership IDs, generations and consent state. A mismatched index/owner tuple returns no rows. The existing account purge drains bounded batches, covers current and retired entries and leaves peers/shared messages intact. Pending initialization cannot recreate a deleting account's queue.
- `retireUnread.ts` removes obsolete private unread markers in jobs of at most 100 entries, re-reading current membership/epoch/generation before each page. Preparation, dismissal, epoch changes, leave and administrative removal enqueue this cleanup. A stale job never deletes current-generation arrivals. Cleanup never deletes canonical messages or public/private observation history. Malformed cross-owner rows fail closed rather than becoming erasure authority. Account deletion retains its separate owner-wide purge for orphaned/retired markers.

This adds only three optional cohort fields (`threads.receiptAudienceRevision`, `threadMembers.receiptAudienceFrom`, `messages.receiptAudienceRevision`) and reuses existing indexes. There is no new table/index or executed migration in this slice. Account-deletion/export changes are a narrow new-table target/projection, not a new authentication or account-deletion flow. No real export, deletion, cleanup or cohort initialization was executed.
