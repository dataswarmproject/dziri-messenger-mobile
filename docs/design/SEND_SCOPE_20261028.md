# Captured Marketplace sends and queue ownership — 28 October 2026

Status: local implementation and synthetic qualification in Consumer, Business and standalone DM. The complete remaining goal stays active. Push is hard-disabled. No production/schema/API publication, master push, real communication, account/grant modification, cloud spend or APK distribution ran.

## Evidence and behavior

The regression first demonstrated that the canonical Marketplace writer accepted a queued payload under a replacement authorized staff identity. Current authentication and conversation access alone did not retain the account/grant that initiated the send. A second regression showed that DM could acknowledge its local queue using another participant's `clientMessageId`.

Canonical Marketplace sends now accept an optional captured `commandContext` with expected actor and full durable authority digest. Both are constraints on fresh server authentication and current write authority, never permission grants. They are checked before idempotency acknowledgement, message creation, typing cleanup, customer projections or timeline writes. Same-clock role loss/re-grant invalidates the old digest; a fresh, currently authorized acknowledgement can still resolve an already committed identical command without duplicating it. Write context is independent of read-sharing preferences and is projected only while current write authority exists. No new schema table or data backfill is needed.

All three Marketplace producers use immutable actor/conversation/store/company context. The server advertises `features.marketplaceWriteScope === 1`; newer clients keep drafts and disable sending when capability or matching write projection is unavailable, rather than downgrade to an unbound request. Legacy callers remain compatible with the optional argument and are not thereby qualified against stale queued identity. The captured metadata never selects the authenticated actor.

- Consumer retains the original command key, body, attachments, reply and send context on retry, including when Messenger appearance/preferences are disabled. Own canonical `clientMessageId` now identifies confirmation instead of a timestamp collision. A grant change holds the old attempt as failed; reviewing it keeps the text as a draft for a new explicit intent. Late upload or send results cannot clear or attach to a newer grant's draft.
- Business retains the key/context for a retry of unchanged content and rejects rebinding it to a replacement grant. A review action retains the draft before a new explicit submission. Late acknowledgements and upload results cannot change the newer grant's draft. Text can still be drafted while sending is unavailable.
- DM stores captured scope inside its existing encrypted-account outbox journal. Snapshots and retry/restoration preserve it. Malformed metadata fails validation; legacy/unbound recovered sends remain failed, with no automatic stamping of a new grant. Actual transport checks the retained scope against the current one before dispatch; the server checks it again at commit. Changing grant disposes the old media composer and resets reply selection while retaining the same encrypted text-draft namespace. This is local component/storage evidence, not physical interruption qualification.
- DM's personal and Marketplace queue confirmation now uses only messages authored by the current account. Another participant or employee cannot confirm this account's pending identifier.
